# Eval datasets

Labelled synthetic Azure estates. Each file holds **both halves** — the estate and
what the correct output is — so a reviewer sees them side by side. Splitting them
across two files makes it easy for one to drift from the other, and a label that no
longer matches its estate is worse than no label.

**Every byte here is synthetic.** No real client's estate, no real subscription id, no
real resource name. Subscription ids use the nil-prefixed form
(`00000000-0000-4000-8000-…`) that no real Azure tenant issues, and
`scripts/check_no_real_data.py` is run over these files by a test.

## The datasets

| Id | Tier | What it is for |
| --- | --- | --- |
| `baseline-mixed` | smoke | One healthy and one wasteful resource of each kind the detectors cover, so precision and recall are both measurable. The broadest coverage in the fewest resources. |
| `adversarial-lookalikes` | full | The two ways a cost detector is wrong in the field: a resource that is idle or stale *by design* (a DR standby, a compliance-retained snapshot) and a wasteful one that looks healthy (a machine just above the rightsizing threshold). |
| `injection-control` | full | The benign half of the prompt-injection differential. |
| `injection-hostile` | smoke | The same estate with attacker-controlled names and tags. Compared against its control: the advice must be identical. |
| `anomaly-shapes` | smoke | The four shapes a daily cost series takes — step change, reverting spike, seasonal pattern, steady — one per subscription. Two must be found and two must not. |

The **smoke** tier runs in the normal CI job on every commit and completes in a few
seconds. It is a genuine subset — `baseline-mixed` for detector coverage,
`injection-hostile` for the security gate (which pulls in its benign twin
automatically) and `anomaly-shapes` for the seasonal non-event — and it enforces every
gate. A smoke run that skipped the gates would be worse than none, because it would
look like coverage.

`anomaly-shapes` is in the smoke tier for one specific reason: a detector that
regresses on the seasonal case reports a client's weekly batch window as an anomaly
*every week*, which makes the whole alerting feed unreadable. That is a failure worth
catching on every commit rather than on every merge to `master`.

## Ground truth is committed, not recomputed

Each wasteful resource carries the **exact** monthly saving the pipeline should
report, as a decimal a human derived from the stated rules and the committed price
catalogue, and reviewed once.

The tempting alternative is to compute the expected figure at scoring time from the
same catalogue. That would make the cost-figure gate compare a calculation to itself
and pass unconditionally. The cost of committing it instead is that refreshing the
price catalogue breaks these files loudly — the same bargain the savings assertions in
`tests/test_graph.py` already make, and the right way round.

A label may say the expected saving is **unknown** (`null`). That is a real answer,
not a gap: a database already on the smallest tier the catalogue carries has no
cheaper target, and a tool that reported its full cost as a "saving" would be claiming
a figure for an action it cannot name.

## Spend series, and labelling a subscription

A subscription may declare a `series_shape` and a `daily_baseline` instead of taking
the estate's flat `daily_spend`. The series is then generated by
`costsentinel.providers.mock.synthetic_series` — the *same* function the demo estate
uses, so a dataset cannot hold a second idea of what a step change looks like, and a
change to the generator moves both together or neither.

Flat remains the default and is not laziness: a flat series makes the observed-spend
figure exact, which is what lets the cost-figure gate assert it to the cent. Every
dataset about waste wants that.

`subscription_labels` records the right answer about each subscription's **spend**,
which is a separate question from whether its resources are wasteful. Once one
subscription is labelled they all must be — the same rule as for resources, for the
same reason: an unlabelled subscription is neither a true positive nor a false one, it
is uncounted. A label that expects an anomaly must also name the `expected_kind`,
because a spike and a level shift send a client to different places and getting the
shape wrong is getting the finding wrong.

## Prices come from the catalogue

A dataset names a SKU, a state, a size and whatever was measured.
`evals/harness/provider.py` prices it from
`src/costsentinel/providers/data/price_catalogue.json` — the same path the mock
provider and the real provider use. So a dataset cannot assert a price Azure does not
charge, and a SKU the catalogue does not cover reports an explicitly unknown cost
rather than a guess.

## Adding a dataset

1. Write the file. `evals/harness/dataset.py` is the schema; validation is strict and
   will tell you what is missing.
2. Label **every** resource and reservation, including the healthy ones. An estate of
   nothing but waste cannot measure precision, and an unlabelled resource is neither a
   true positive nor a false one — it is simply uncounted, which is the worst of the
   three.
3. Give every label a `note` saying **why** that is the right answer. Mandatory, and
   enforced: a future disagreement should be with a stated argument rather than with a
   bare boolean.
   Set `expected_exemption` when the right answer is "surfaced, and deliberately not
   actioned" rather than "not waste".
4. Derive each expected figure from the rules in `src/costsentinel/agents/savings.py`
   and the catalogue. Do not read it off a run — that is how ground truth stops being
   ground truth. (Three of the baseline figures were wrong on the first attempt, and
   the harness caught all three. Working out which side was right is the work.)
5. Run `uv run costsentinel eval` and regenerate `evals/REPORT.md`.

## "Handled correctly" is not the same as "not flagged"

`expected_exemption` names a resource that should be **detected as waste and then
held back**: it must appear in the report's flagged-but-exempt section with that
reason, and must not appear among the actionable findings.

The distinction carries more weight than it looks. "Not recommended" is reachable two
ways -- by exempting a resource, or by failing to notice it -- and only one of them is
correct behaviour. A disaster-recovery standby *is* idle, and a snapshot held for six
years *is* stale. The honest answer is to say so, say which tag withholds the advice,
show what the resource costs, and leave that figure out of the savings total. A
scoring rule that accepted mere absence would award full marks to a system that never
noticed the standby at all, which is a different and worse system -- and it would hide
a real cost behind a compliance obligation the client may be able to meet more
cheaply.

So a label that expects an exemption is `is_wasteful: false` (it is not actionable
waste, so it is not in the precision denominator) *and* carries
`expected_exemption`, which is what makes the exemption itself part of the ground
truth.

## A note on these cases' history

All three of `adversarial-lookalikes`' hard cases **failed** when the dataset landed
in Phase 5, and that was deliberate. The labels recorded three real gaps: no tag
exemption, so a DR standby was flagged as idle and a HIPAA-retained snapshot as stale;
and rightsizing thresholds that let a genuinely oversized machine hide just above
them. They were in the dataset to make the gaps measurable rather than to hide them.

Phase 6 closed all three, which is the sequence working as intended: measure first,
then fix, so that neither number is a guess. The scorecard moved from 0/3 to 3/3 and
detection precision and recall both reached 1.00. If a future change reopens one of
them, these labels are what will say so.
